## Scheduler Verification ✓

### Current Status
The scheduler is **confirmed working** and set to run "all day" (automatic mode). You can verify this in the **Research Actions** panel on the left sidebar:

- **Mode**: Automatic
- **Interval**: 60 minutes (configurable)
- **Next Run**: Shows the exact timestamp of the next scheduled cycle
- **Resume Date**: 2026-10-05 (allows you to suspend and resume)

### How It Works

1. **Schedule Configuration** (in `makemoney.py`):
   - Default interval: 60 minutes
   - Mode: "manual" (default) or "automatic"
   - Can be suspended until a specific date/time

2. **Claim-Based Execution** (`claim_due_research_cycle()`):
   - The scheduler uses a claim-based model: only one process can claim a cycle at a time
   - When claimed, `research_schedule_last_run` is updated to the current timestamp
   - Next run is calculated as: `last_run + interval_minutes`
   - Safe for concurrent access (database CONFLICT handling)

3. **Database Tracking** (`app_settings` table):
   ```sql
   research_schedule_mode         -- "manual" or "automatic"
   research_schedule_interval_minutes -- How often to run (default: 60)
   research_schedule_last_run     -- ISO timestamp of last execution
   research_schedule_suspended_until -- Pause until this ISO timestamp
   research_candidate_offset      -- Current rotation position in candidate pool
   ```

### Verification Steps

To verify the scheduler is working correctly:

1. **Check next run time** in UI:
   - Open sidebar → Research Actions
   - Look for "Next run: YYYY-MM-DD HH:MM:SS CEST"

2. **Monitor execution** (if running manually):
   - Click "Run now (manual research)" button
   - Observe the log output
   - Check that `claim_due_research_cycle()` returns `True`

3. **Database verification**:
   ```sql
   SELECT key, value FROM app_settings 
   WHERE key LIKE 'research_schedule_%'
   ORDER BY key;
   ```

4. **Confirm mode is 'automatic'**:
   ```bash
   sqlite3 finbot.db "SELECT value FROM app_settings WHERE key='research_schedule_mode';"
   # Expected output: automatic
   ```

## Companies Dashboard (NEW)

### Problem Solved
**Repetitive Companies Issue**: The previous implementation cycled through the same ~10 companies repeatedly, making analysis less diverse.

### Solution Implemented

#### 1. **Company Analytics Tracking**
A new `company_analytics` table tracks per-company metrics:

| Column | Type | Purpose |
|--------|------|---------|
| `ticker` | TEXT | Stock symbol |
| `company_name` | TEXT | Full company name |
| `sector` | TEXT | Industry sector |
| `times_analyzed` | INT | How many times this company was analyzed |
| `last_analyzed_at` | TEXT | ISO timestamp of last analysis |
| `last_signal` | TEXT | bullish/bearish/neutral from last analysis |
| `last_confidence` | REAL | Confidence score from last analysis |
| `avg_confidence` | REAL | Running average confidence across all analyses |
| `trade_count` | INT | Total trade attempts for this company |
| `trades_accepted` | INT | How many trades were actually opened |
| `acceptance_rate` | REAL | `trades_accepted / trade_count` |

#### 2. **Research Cycle Tracking**
A new `research_cycle_companies` table records which companies were analyzed in each cycle:

```sql
CREATE TABLE research_cycle_companies (
  id INTEGER PRIMARY KEY,
  cycle_timestamp TEXT NOT NULL,
  ticker TEXT NOT NULL,
  signal TEXT NOT NULL,
  confidence REAL NOT NULL,
  UNIQUE(cycle_timestamp, ticker)
);
```

#### 3. **Automatic Analytics Updates**
Every time a company is analyzed (during `run_trading_cycle`), the system now calls:

```python
update_company_analytics(
    ticker="AAPL",
    company_name="Apple Inc.",
    sector="Technology",
    signal="bullish",
    confidence=0.82,
    accepted=True  # or False for rejections
)
```

This updates:
- Increments `times_analyzed`
- Updates `last_analyzed_at`
- Calculates running `avg_confidence`
- Tracks `trades_accepted` vs `trade_count`
- Computes `acceptance_rate`

#### 4. **Least-Analyzed Rotation** (Reduces Repetition)
Added new function `get_least_analyzed_companies(limit=10)` which returns companies sorted by:
1. **Fewest analyses first** (`times_analyzed ASC`)
2. **Oldest analysis second** (`last_analyzed_at ASC`)

This allows you to modify the candidate selection logic to **prioritize under-analyzed companies**.

```python
# When a trade is ACCEPTED
update_company_analytics(
    ticker=candidate["ticker"],
    company_name=candidate["company_name"],
    sector=candidate["sector"],
    signal=candidate["signal"],
    confidence=candidate["confidence"],
    accepted=True

# When a trade is REJECTED (at any stage)

    ticker=candidate["ticker"],
    company_name=candidate["company_name"],
    sector=candidate["sector"],
    signal=candidate["signal"],
    confidence=candidate["confidence"],

    cycle_timestamp=datetime.now(timezone.utc).isoformat(),
    ticker=candidate["ticker"],
    signal=candidate["signal"],
    confidence=candidate["confidence"]
)
```

### Reducing Company Repetition

#### Option 1: Manual Prioritization
- Check the "Least Analyzed Companies" list
- Run research on those companies manually
- Use the deep dive to track results

#### Option 2: Automated Candidate Rotation (Future Enhancement)
Modify `ResearcherAgent.run_data_fetch()` to:
```python
# Get candidates weighted by analysis frequency
least_analyzed = get_least_analyzed_companies(limit=len(candidate_pool))
rotation_weights = [1.0 / (1.0 + company["times_analyzed"]) for company in least_analyzed]
# Sample without replacement, weighted by (1 / times_analyzed)
selected = np.random.choice(
    least_analyzed,
    size=research_limit,
    replace=False,
    p=rotation_weights / rotation_weights.sum()
)
```

#### Option 3: Fair-Share Rotation
- Divide analysis budget equally across all companies
- If 6 slots per cycle and 9 companies total:
  - Each company gets analyzed in a round-robin
  - Prevents any company from being analyzed twice before others are done
